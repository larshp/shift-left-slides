Shifting Left in ABAP
Step 1

Visibility

  • To collaborate, the team needs to see the same thing.
  • Documentation and code changes live in one common, versioned place.
  • Everyone sees the latest feedback, the ongoing changes, and what has happened.

Why it matters

Publishing code triggers automated feedback for the developer — and colleagues can follow progress and influence a change early, not weeks later.

Shifting Left in ABAP
Step 2

Static analysis

  • Some of the quickest feedback available.
  • Every code change is checked automatically.
  • When something breaks, bisect the history to find exactly which change did it.
  • This is the heart of Continuous Integration.

Tool that works well

abaplint

Linting and checks on every push, outside the ABAP system.

Bisect the history

Every change checked → the first failing one is the culprit.

Shifting Left in ABAP
Step 3

Unit tests

  • Write unit tests, and run all of them on every change.
  • It may take a few minutes — far better than forgetting to run them and leaving failures behind.
  • Nobody has to remember anything.
  • A failure points at the change that caused it, while it's still fresh.

In practice

ABAP Unit on GitHub Actions

Running ABAP Unit tests in CI has been possible since at least 2021.

Step 4

UI & end-to-end tests

  • Test the user interfaces.
  • Spin up external systems in Docker to verify integrations end to end.
  • Test cases evolve alongside the code changes.
  • A change that breaks a test must fix it — and reviewers can see whether tests were added.

Real dependencies

Docker

Disposable copies of the systems you integrate with, started for each run.

Anti-patterns

Feedback that arrives too late

Feedback at transport release
By then refactoring is costly. Shift left and release with confidence.
Manually triggering checks
Publishing a change runs all analysis and unit tests automatically — and makes a backup.
Reviewing a moving target
Code in an ABAP system can change mid-review. Review versioned code, so developer and reviewer see the same state.
Weekly tests in Quality
“Who broke something?” Still test in Quality, but treat failures as feedback to catch it earlier next time.

Put ABAP code in Git

Inner sourcing
